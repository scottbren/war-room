## 2026-11-03: Contract change (APPROVED by the user): three more floor ids

`FloorId` in `packages/content/src/schemas/common.ts` grows from four ids to seven: added `lower` (basement, indoor), `shore` (open-air, below the lawn) and `hill` (open-air, raised). Reason: the user wants a modern stacked-volume villa and a terraced site (hill, house, shore) with a basement; one flat elevation per floor could not express that. Nothing else in the schemas changed and existing maps stay valid. Tooling follows: the validator treats `grounds`, `shore` and `hill` as open-air (link ends may be outdoors; a tunnel may exit there), the greybox gets keys 5-7 and a shared `allFloorsVisible()`. Still open: window shutter and smart-home runtime state (see the v3 entry).

## 2026-11-03: Contract change (user-approved): smart-home state in the sim

The user said to go ahead and wire up the smart house after being told it needs new state in the frozen public sim types. Added: `Command` kinds `setDevice`, `setShutter`, `setAlert`; `SimEvent` kinds `device`, `shutter`, `alert`; `Snapshot` fields `devices`, `shutters`, `alert`, `hubOnline`; saved-state version 2. Devices come from `smart:<kind>` markers (a lock names its door with `door:<id>`); shutters from windows with `shutter: true`. A new `smartHomeSystem` runs after perception: each alert level fires its automation once (1 floodlights on, 2 shutters close, 3 working locks lock their doors) and only while a hub is on; missed levels (no hub) are not replayed later. Nothing raises the alert yet: perception and combat will, in later tasks. The snapshot carries simulation truth, so the UI and LLM prompts must filter it through a knowledge layer (golden rule 4) before showing it to the player. Technical-design pipeline order updated (smart home is step 5).
